

Without Istio:
- Any microservice can talk to other microservices directly.
- No visibility into who is talking to whom.
- No control over encryption or traffic rules.

With Istio:
- Every service gets a sidecar container, which is also called an Envoy proxy. This is automatically injected.
- All traffic flow goes through this proxy only.
- We get security and traffic control without changing, improving, or modifying our application code.

We don't use Istio for basic or small microservice architecture projects as this makes a simple architecture complex.

This helps us to achieve zero-trust security. In zero-trust security every request will be validated and tested before it is sent to the application. 

---

East-West Traffic : East-west traffic represents internal service-to-service communication. East-west traffic typically forms the vast majority of total network data inside a production cluster.

It will be managed by CNI (container network interfaces). 
Pods do not directly communicate with other pods. 
Pods will use services i.e; cluster IP primarily to communicate with other services.

Kube-proxy runs on every node to intercept traffic sent to cluster IP. 

----

North-South Traffic : North-south traffic acts as the front door and back door of our infrastructure. Whatever client request comes from the outside world, it will be picked up. We have a lot of options, like ingress controllers and Kubernetes services like NodePort or LoadBalancer. These components take the traffic coming from the outside world from the clients and then send the traffic to the Kubernetes cluster's internal workload. 

-----

1. istiod / Control plane : this is a brain of ISTIO. It has multiple components like pilot - Traffic rules, citadel - certificates, and galley - configuratio validation. 
2. Sidecar container / Envoy proxy : 
3. mTLS / peerAuthentication : 
	3.1 STRICT : only mTLS is accepted. Any plain HTTP request will be rejected if we set strict mode. 
	3.2 PERMISSIVE : Accepts plain HTTP requests as well as mTLS requests. 
4. Gateway : gateway manages inbound traffic from outside of the cluster, similar to an ingress controller, and works with the Kubernetes Gateway API.
