K8s Architecture : 

1. Control Plane : Brain of K8s
2. Data Plane : Hands of K8s


1. CONTROL PLANE COMPONENTS

1.1 kube-apiserver / API Server:
--> This is the front door of K8s. This is the only point of contact to the couster for us.
--> If you want to deploy a new workload, you run "kubectl apply" and talk to api to create workload.
--> It validated the confoiguration first (pod, deployment, service)

1.2 etcd:
--> etcd contains all the information about the k8s cluster and workload.
--> Data stores as key-value pairs (tags)
--> Treat it as k8s Database
--> it stores current and desired state of the cluster.
--> if etcd is gone, the cluster state is lost.

1.3 kube-scheduler: 
--> kube-scheduler looks for availbale worker node to run our workload based on node's resources (i.e; cpu / memory).
--> This wont run the pod, it will picks the best node to run our workload. 

1.4 kube-controller-manager: 
--> Act as Supervisor, This monitors the ETCD and ensure our appliation's current state matches the desired state.
--> If we ask for 3 replicas, and only 2 are running... Then this send instructions to scheduler to pick a node and then it creates a replica.
--> This runs background loops to etcd and make sure desired state and actual state matches.

1.5 Cloud Controller Manager:
--> Connects the k8s to the cloud resources for utilising resources i.e; LB, Roles, VPC..


2. DATA PLANE / WORKER NODE : 

2.1 kubelet : 
--> Kubelet is an AGENT runs in every worker node.
--> It listens to the control plane and ensure that the containers described in the pod specifications are running and healthy.?
--> If container goes down, the kubelet restart it locally, automatically.

2.2 Kubeproxy:
--> This is a networking component, that runs on Every Node. 
--> This assigns IPs to every pod created on Worker nodes.
--> Its network proxy that runs on each node. THis handles network communications inside and outside of our cluster, THis ensures traffic reaches the right contianer.

2.3 Container Runtime: 
--> Responsible for pulling images and running containers.
--> K8s uses cri-o and containerd as runtime. (it used to support docker earlier)
--> kubelet asks container runtime to pull the image and start the container inside the pod. 


pod : Its the smaller deployable unit in K8s. A pod is a wrapper around Container. 
Generally one pod cotnains one Container. Pod is not limited to one container.

A pod can cotnains multiple containers also.. (second container called as sidecar cotnainer)

AWS takes care about the CONTROL PLANE Components.
For HA, FT of CONTROL PLANE, AWS Maintains multiple Copies across 3 AZs (almost 6 copies)..

--> AWS automatically provision, configure and manage ec2 instances for worker nodes.
--> We need to handle the scaling.
--> We have to choose right sized ec2 instances.

EKS Auto Mode : AWS automatically pickls the required compute resources.

AWS Fargate : serveless, No nodes to manage.. Can directly deploy pods.

K8s has 3 types of scalings.

1. HPA : Horizontal Autoscaler : Based on Pods CPU/memory, Pod count will increase / decrease.
2. VPA : Virtical Autoscaler : This will adjust the existing Pod's CPU/Memory, THis required pod to restart. (We dont use much in real environments)
3. Cluster AutoScaler : K8s adjust the nodes based on the pod count: Add/Remove instance from node group.

We have 4 update modes in VPA.

Off : It only shows the suggestions, does not apply changes.
Initial : Applies recommendations only during the pod creation. Running pods are never touched.
InPlaceOrRecreate: Attempt to resize CPU/Memory on the fly wihtout restarting the pod. Fall back to eviction if node capacity ot runtime limits prevent it.
Recreate: It evicts the running pods to create new pods with updated resources.

requiredDuringSchedulingIgnoredDuringExecution : Strict requirement.

requiredDuringScheduling: HARD RULE :  this is a mandatory rule that the kube scheduler must follow when deciding where to place a new pod. 
--> If the scheduler cannot find a node that perfectly matches our criteria, the pod will not be scheduled. 

IgnoredDuringExecution: once a pod is successfully running on a node, Kubernetes will not continuously re-evaluate this specific rule against the node. 
--> If someone removes or modifies the label on the node while the pod is active, Kubernetes will not evict or terminate the pod. The pod will safely continue running until it finishes the work or is manually deleted. 

---

preferredDuringSchedulingIgnoredDuringExecution : Soft preference/requirement.

preferredDuringScheduling : this is a soft preference. If there is any node that matches with the label, it will obviously run there. If a node has that label, it will run elsewhere. That's why we call it a soft preference.

Node Drain : the drain evicts all pods from a node gracefully. This is commonly used:
1. node maintenance
2. decommissioning a node
3. cluster upgrades

Flags: 
--ignore-daemonsets : Skip DaemonSet pods. They run on every nodes.
--delete-emptydir-data : Delete pods that are using emptyDir volumes.
--timeout=60s : Fail if the drain takes longer than 60 seconds.

After a node is drained three things happen:
1. The node is marked as scheduling disabled (cordoned).
2. No new pods will be scheduled on this node.
3. Existing pods are evicted and rescheduled on other nodes.

kubectl drain ip-192-168-13-127.ap-south-1.compute.internal --ignore-daemonsets --delete-emptydir-data --timeout=120s --force

kubectl describe nodes ip-192-168-13-127.ap-south-1.compute.internal

kubectl uncordon ip-192-168-13-127.ap-south-1.compute.internal

--> Our workload is not going to redistribute or rebalance across the nodes automatically if you uncordon a node. We can run the command below so the workload is going to automatically distribute. 

kubectl rollout restart deployment mynginx

Liveness Probe : Is our container alive.? 	If failed: Container is restarted.

Readiness probe : Is container ready to serve traffic.?	If failed: Pod is removed from the service.

Startup probe : Has the container finished starting.?	If failed: Container is killed and restarted.



initialDelaySeconds 	: Wait before first check.
periofSeconds 			: perform the Checks for every "x" seconds.
failureThreshould 		: Restart after "x" consecutive failures.

** 
1. Pods won't receive traffic until the readiness probe has passed.
2. Startup probe configuration helps a slow-starting application.
3. Liveness probe and readiness probe won't start until the "startup probe" has succeeded.

PDB : pod Disruption Budget : PDB tells Kubernetes the minimum number of pods that must always remain up and running when the cluster undergoes node and pod disruptions. 

minAvailable :  Let's assume we have a deployment with 5 replicas. We can set minimum available to 4. 
--> Kubernetes will only allow draining and killing one pod at a time. It will wait for that one pod to successfully restart on a new node before it allows or touches the next one. 

maxUnavailable : we can define the maximum number of parts that are allowed to be offline at any given moment. 

--> THis is not applicable for: 
Involuntary Disruptions i.e; Hardware failures
Unmanaged Pods (creating a pod without replicaset and deployment)
Direct pod deletions

EKS AutoMode: this is a new option in AWS EKS. In regular EKS we have models like a managed node group so we need to manage the nodes or the data plane. AWS manages the control plane but in AWS EKS auto mode AWS manages the control plane as well as the data plane.

Below are the points which explain the auto mode advantages:
1. Compute auto-scaling is built-in.
2. Pods and service network also in-built. 
3. It can pick spot instances as well as on-demand instances combined.
4. Auto mode picks the right size configuration automatically.
5. We can configure a node pool with the required instance configurations, like on-demand and spot types.

EKS fargate: Serverless, No Node at all, Entire workload run as pod.

EKS Fargate has some limitations:
- EKS Fargate uses the cold start method. Because of cold start pod creation or pod scaling generally takes 30 to 90 seconds.
- The EKS Fargate method does not support daemon sets.
- We cannot use EBS with the Fargate method. If you want to have shared storage we can use only EFS.
- EKS Fargate workload supports a maximum of one individual pod with 16 vCPU and 120 GB of memory only.
- It has a lot of non-compliance standards. EKS Forge is not compatible with or compliant with PCA, DSS, HIPAA, FedRAMP, and SOC 2.
