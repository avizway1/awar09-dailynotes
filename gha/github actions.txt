

Github Actions: it's a CI/CD platform built in GitHub. It helps us to automate tasks like building, testing, and deploying the code from our repository. Whenever any developer commits any changes to the GitHub repository, it will pick up the changes. It can perform the automated operations like building the code, testing the code, scanning for the changes, and deploying the changes to the server. It is going to perform all those operations automatically. 

Prior to these GitHub Actions we used tools like Jenkins but now Jenkins is a bit outdated. Organisations are migrating to or using GitHub Actions a lot. 

Below are the reasons why GitHub has become more popular in recent times:
- Native GitHub integration
- Easy YAML configurations
- Multi-operating system support - Linux, Windows and macOS
- Matrix builds	- test across multiple versions at the same time.
- 2000 minutes per month for private repos and unlimited runs for public repos.

Core components of GitHub Actions 

1. Workflow : a workflow is a complete automation defined in a YAML file. This is generally stored in `.github/workflows` inside our repo. 

Our REPO
	|
	|_ .github/
		  |
		  |__ workflows/
		  			|
					|__ file.yaml		--> The workflow file


2. Event : an event is a trigger that actually starts the workflow. Common events are:
- push				- When code is pushed
- pull_request		- When a PR is created
- scheduled			- Specific time or intervals using CRON
- workflow despatch	- Manually trigger from the UI


3. Job : a job is a group of steps that runs on the runner. 

4. Step : a single task inside a job can run a shell command or it can use an action. One job can have multiple steps also. 

5. Runner : a runner is nothing but a virtual machine that executes our jobs. We have two options:

- GitHub-hosted runner: GitHub provides Ubuntu, Windows, and Mac operating systems.
- Self-hosted: We can prepare our own server and add it as a self-hosted runner so all the jobs run inside our own server.

6. Action : it's a reusable piece of code that does a specific task. We can use actions from GitHub Marketplace. GitHub has approved actions and verified publishers like AWS and Microsoft. We can pick it and use it instead of writing multiple commands.

In GHA, we have three types of variables:
1. Workflow variables: 			we can define these in our YAML file. $VAR_NAME
2. Configuration variables: 	we can define these in the GitHub UI. ${{ vars.VAR_NAME }}
3. Context variables: 			automatically defined by GitHub		  ${{ github.VAR_NAME }}

https://docs.github.com/en/actions/reference/workflows-and-actions/contexts


Workflow variable again has three options:
1. Workflow level: If we define any variable at workflow level, it is available to all jobs and steps.

name: 01 - my first job
on:
    workflow_dispatch:
env:
	CLOUD: AWS Cloud
jobs:
    my-first-job:
        runs-on: ubuntu-latest
        steps:
            - name: run single command
              run: echo "I AM using $CLOUD"


2. Job level: If we define any variable at job level, it is available only within the job.

name: 01 - my first job
on:
    workflow_dispatch:
env:
	CLOUD: AWS Cloud
jobs:
    my-first-job:
        runs-on: ubuntu-latest
		env: 
			SUBJECT: vpc
        steps:
            - name: run single command
              run: echo "I AM using $CLOUD"
            - name: run single command
              run: echo "I AM using $CLOUD and now learning $SUBJECT"

3. Step level: If we define any variable at step level, it is available to that one particular step.

A self-hosted runner is a machine that we own. It may be an EC2 instance, an on-premises server, or our own laptop that actually runs our GitHub Action jobs.

Instead of GitHub providing the machine, we are providing our own machine to run the job.

Below are the advantages that we get when we are using a self-hosted runner:
- Need access to a private VPC or databases? The best option is a self-hosted runner.
- Need custom hardware like specific GPUs, ARMs, and memory.
- If we want to have preinstalled tools like Docker, kubectl, or node-specific versions.
- For jobs that take longer than 6 hours, we can go with the self-hosted runners.
- Need to deploy to internal servers?

CAST : Comprehensive Testing : a methodology that combines multiple security tools. We can treat this as a mixed box that looks at the code, looks at the running application, and checks the third-party applications and integrations. 
With CAST generally we find coding flaws, runtime errors, and vulnerable open-source libraries. 
This will be part of the software lifecycle. 

SAST : Satic Application Security Testing : bandit, sonarcloud/sonarqube
It is a single tool that scans uncompiled source code. 
The testing style is white box testing. It will inspect or check the entire code structure. With SAST scanning we can find coding practises, hard-coded passwords, and structural flaws. SAST comes into a primary shift-left mechanism. Shift left means we can identify the issue early in the development, when the developer is actually writing the code.



Why Sonarcloud: Sonar Cloud supports almost 40+ programming languages and frameworks.

We have quality gates. It acts as a go/no-go filter. It stops the code from processing if it fails to meet specific metrics like low code coverage or high bug density. 

Bugs : it's a code error that will cause functional failure. 
Vulnerabilities: a security weakness that can put our application at risk of exploitation 
Code Smells : Poorly structured code that is not actually broken but it makes maintenance difficult 

Duplication : Sonar can highlight the duplicated code blocks to prevent redundancy.

Once our project's initial analysis is completed, we need to disable automatic analysis as this will conflict with the code pipeline. For that:
1. Go to Sonar Cloud.
2. Choose the project.
3. Click on Administration in the bottom left sidebar.
4. Click on Analysis Method.
5. Choose Analysis as Off.

Why: Sonar Cloud cannot run two analysis methods at the same time. If we keep this enabled we will get an error: "You are running CI analysis while automatic analysis is enabled."
